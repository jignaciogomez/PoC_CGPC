# PoC_CGPC: ADF and Databricks promotion

The existing ADF factory `dev-cgpc-poc` is Git-connected to this repository with collaboration branch `Dev`, publish branch `adf_publish`, and root folder `/adf`. The ADF resource JSON therefore belongs directly under `adf/pipeline`, `adf/linkedService`, and `adf/factory`.

This proof of concept has one ADF pipeline, `PL_LoadOrders`, that runs a Databricks notebook. The notebook creates a demo Delta table and view under the selected Unity Catalog:

| Stage | Git source | ADF factory | Databricks catalog | Promotion action |
| --- | --- | --- | --- | --- |
| DEV | `Dev` | `dev-cgpc-poc` | `dev_bronze_ca` | Author and Debug in ADF; Publish for DEV Live mode |
| QA | reviewed `QA` branch | existing QA factory (name to configure) | `qa_bronze_ca` | GitHub Actions exports ARM and deploys QA |
| UAT | reviewed revision | UAT factory to provision | `uat_bronze_ca` | Future protected workflow/environment |
| PROD | reviewed revision | PROD factory to provision | `prod_bronze_ca` | Future protected workflow/environment |

The same notebook creates `sales.orders_demo` and `sales.v_orders_by_country` in the target catalog. For example: `dev_bronze_ca.sales.orders_demo` and `qa_bronze_ca.sales.orders_demo`.

## How this repository uses ADF Git branches

ADF Studio writes collaboration JSON into `Dev` under `/adf`. The `adf_publish` branch is generated by ADF Studio when someone selects **Publish**; it is useful for DEV Live mode. The QA workflow uses the [ADF automated export utility](https://learn.microsoft.com/en-us/azure/data-factory/continuous-integration-delivery-improvements) against the reviewed `QA` branch, so QA deployment does not require copying files from `adf_publish` or editing `dev` strings in source. Create a PR from `Dev` to `QA` after the QA resources and GitHub settings exist. Review and merge it; the push to `QA` starts the deployment workflow. Manual dispatch will also be available once this workflow file is present on the default `main` branch, as required by GitHub.

`adf/arm-template-parameters-definition.json` exposes the Databricks workspace host/resource ID, cluster ID, notebook path, and catalog for deployment. The script checks the *actual* ARM export before writing QA parameter values. The bundle resolves the QA notebook path; the workflow passes that path to ADF. This follows [ADF custom parameter rules](https://learn.microsoft.com/en-us/azure/data-factory/continuous-integration-delivery-resource-manager-custom-parameters) and [Databricks bundle resolved configuration](https://learn.microsoft.com/en-us/azure/databricks/dev-tools/bundles/variables).

## First-time setup

1. **DEV Databricks:** Supply the real workspace URL/resource ID and cluster ID in `adf/linkedService/LS_Databricks.json`. The current `replace-with-dev-*` values are placeholders. Set `DATABRICKS_HOST` and `BUNDLE_VAR_cluster_id`, then deploy the `dev` bundle target. Run `databricks bundle validate -t dev --output json` and copy `resources.jobs.load_orders.tasks[0].notebook_task.notebook_path` into the ADF pipeline JSON. Then test in ADF Studio. The initial notebook path is also a placeholder.
2. **Catalogs and permissions:** Run `databricks/sql/bootstrap_dev.sql` in DEV and `bootstrap_qa.sql` in QA as an authorized catalog creator. Grant the notebook run identities the needed catalog and schema privileges. The ADF managed identities need access to their respective Databricks workspaces, clusters, and deployed notebook folders. Keep QA identity access scoped to QA data.
3. **QA resources:** Create a QA ADF factory and QA Databricks workspace/cluster, and enable the QA ADF factory's system-assigned managed identity. The workflow deploys application definitions; it does not provision factories, workspaces, clusters, Unity Catalog grants, or network access.
4. **GitHub `qa` environment variables:** `DEV_FACTORY_RESOURCE_ID` (full Azure resource ID for `dev-cgpc-poc`), `QA_ADF_RESOURCE_GROUP`, `QA_ADF_FACTORY_NAME`, `QA_DATABRICKS_HOST`, `QA_DATABRICKS_WORKSPACE_RESOURCE_ID`, and `QA_DATABRICKS_CLUSTER_ID`.
5. **GitHub `qa` environment secrets:** `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, and `AZURE_SUBSCRIPTION_ID`. Configure [Azure OIDC federation](https://learn.microsoft.com/en-us/azure/developer/github/connect-from-azure-openid-connect) for that identity, permit ARM deployment in the QA resource group, and grant it Databricks bundle deployment access. Protect the `QA` branch and `qa` environment if approvals are required.

The default QA deployment installs the notebook/job and ADF definitions; it does not run the sample pipeline. For an end-to-end check, manually dispatch **Deploy reviewed QA branch** from `QA` with `run_smoke_test=true`. This recreates the three-row demo table and view and waits for the ADF run to finish. Do not point the demo table name at business data.
